# 04 · 数据源与处理 Demo

> 对应分工第 4 项：找到可行的数据源，做一个小型数据处理 demo（采集、清洗、字段描述）。
> 这里的东西**能独立跑**，不依赖主项目的后端服务。

---

## 一、这个文件夹里有什么

```
04_数据源与处理Demo/
├── demo_pipeline.py          采集 → 清洗 → 聚合 三步，约 330 行，只依赖标准库
├── raw/                      真实原始返回体（未做任何加工）
│   ├── search_闪身步_20260925.json
│   ├── search_闪身步_20260926.json
│   ├── search_闪身步_20260927.json
│   └── search_琵琶曲_20260925.json
└── out/                      运行产物
    ├── videos_clean.csv      清洗后的视频级数据（85 行）
    ├── daily_stats.csv       按 梗 × 日 聚合（4 行）
    └── report.md             本次运行的处理报告
```

**`raw/` 里的四份 JSON 是 2026-10-05 用 B 站 `wbi/search/type` 接口真实抓取的原始返回体**，
没有做过任何加工。每份对应「一个梗名 × 一个自然日」，`page_size=30`，
所以原始记录共 120 条。抓取时带了 WBI 签名、匿名设备指纹，请求间隔 2.5 秒。

## 二、怎么跑

```bash
cd 04_数据源与处理Demo
python demo_pipeline.py            # 读 raw/ 下的快照跑（离线、可重复）
python demo_pipeline.py --live     # 现场重新采一次（需要网络，每个梗 1 次请求）
```

只需要 Python 3.10+，**不需要装任何第三方库**（全部用标准库实现，包括 WBI 签名）。

| --- | --- |

## 四、采集层：三个接口与"两种空"

### 4.1 用到的接口

| 接口 | 用途 | 拿到什么 |
| --- | --- | --- |
| `x/frontend/finger/spi` | 取匿名设备指纹 | buvid3 / buvid4 |
| `x/web-interface/nav` | 取 WBI 签名密钥 | img_url / sub_url |
| `x/web-interface/wbi/search/type` | 搜视频 | 见下方字段表 |

Demo 里只用了搜索接口（前两个是签名与指纹的前置调用）。

### 4.2 必须区分的两种"空"

```python
if "v_voucher" in data:      # 被限流吞掉 → 不可信，不能记成 0
    print("命中风控，跳过")
elif not data.get("result"): # 真的没内容 → 可信
    print("空窗")
```

顺序不能反，判断依据不能混。这条规则在本项目的真实库里曾造成 1,412 / 2,036 行假零。

### 4.3 频率控制

Demo 里每个梗一次请求、间隔 2.5 秒。主项目的默认间隔是 1.2 秒（约 0.8 次/秒），
连续 3 个梗撞上硬风控（HTTP 412 / `code=-352`）就中止整批。
**这是刻意保守的**——全库重采约 3,300 次请求，1.2 秒只比 0.35 秒多花半小时。

## 五、字段字典

### 5.1 原始字段（`raw/*.json` 里的 `data.result[]`，节选本项目实际使用的）

| 原始字段 | 类型 | 含义 | 本项目怎么用 |
| --- | --- | --- | --- |
| `bvid` | str | 视频唯一编号（BV 号） | 去重键；前端可点开核验 |
| `aid` | int | 视频 av 号 | 备用标识 |
| `title` | str | 标题（**含 `<em class="keyword">` 高亮标签**） | 相关性打分（0.6 权重）；必须剥标签 |
| `description` | str | 简介 | 相关性打分（0.2 权重） |
| `tag` | str | 逗号分隔的标签串 | 相关性打分（0.2 权重里的关键词覆盖率） |
| `author` | str | UP 主昵称 | 去重作者数（`creator_count`） |
| `mid` | int | UP 主 ID | 主项目用于跨日去重（当前库里只存了名字，是已知缺陷） |
| `play` | int | 播放量 | 播放分（0.25 权重） |
| `danmaku` / `video_review` | int | 弹幕数 | 互动分（评论 + 弹幕） |
| `review` | int | 评论数 | 互动分 |
| `favorites` | int | 收藏数 | 详情页展示；**不进日统计**（避免两个口径混用） |
| `pubdate` | int | 发布时间（Unix 秒） | 日期区间校验；聚合到自然日 |
| `duration` | str | 时长，形如 `"0:38"` / `"1:02:03"` | 需转成秒 |
| `typename` | str | 分区名 | 诊断用 |
| `numResults` | int | **该日期区间内的总结果数** | 存为 `search_total`，年龄中性的活动量参考 |
| `pic` | str | 封面 URL（协议相对，`//i1.hdslb.com/...`） | 前端引用外链，**不转存**（带 Referer 会 403） |

**搜索接口给不到的字段**：`like`（点赞）、`coin`（投币）。这两个要另调
`x/web-interface/view` 逐条补齐，本项目只对头部视频补，用于详情页展示，
**不回灌日统计**——避免"头部有完整数据、长尾没有"造成两个口径混用。

### 5.2 清洗后字段（`out/videos_clean.csv`，共 17 列）

| 字段 | 类型 | 含义 | 生成方式 |
| --- | --- | --- | --- |
| `meme` | str | 梗名 | 来自查询词 |
| `stat_date` | date | 统计日（`YYYY-MM-DD`） | 来自查询区间 |
| `bvid` | str | 视频编号 | 原样，去重后唯一 |
| `title` | str | 标题 | **剥掉 HTML 标签** |
| `author` | str | UP 主昵称 | 原样 |
| `author_mid` | str | UP 主 ID | 原样（保留以便后续跨日去重） |
| `typename` | str | 分区名 | 原样 |
| `tags` | str | 标签串 | 原样 |
| `publish_time` | datetime | 发布时间 | `pubdate` 时间戳 → 本地时间字符串 |
| `duration_seconds` | int | 时长（秒） | `"0:38"` → `38`；`"1:02:03"` → `3723` |
| `view` | int | 播放量 | `play` |
| `danmaku` | int | 弹幕数 | `danmaku`，缺失时退回 `video_review` |
| `reply` | int | 评论数 | `review` |
| `favorite` | int | 收藏数 | `favorites` |
| `relevance_score` | float | 相关性得分（0~1） | 0.6/0.2/0.2 加权，见 [03](03_热度量化方案.md) 1.3 |
| `matched_terms` | str | 命中的词，`\|` 分隔 | 打分过程的副产物，可抽查 |
| `search_total` | int | 区间内总结果数 | `numResults` |

### 5.3 日粒度字段（`out/daily_stats.csv`，共 9 列）

| 字段 | 含义 |
| --- | --- |
| `meme` / `stat_date` | 梗名 / 统计日（联合主键） |
| `video_count` | 当天入库视频数 |
| `creator_count` | 当天去重作者数（**注意**：实测与 `video_count` 中位数比 = 1.000） |
| `view` | 当天头部样本播放合计 |
| `interaction` | 当天评论 + 弹幕合计 |
| `favorite` | 当天收藏合计 |
| `search_total` | 当天区间内总结果数 |
| `observed` | **是否真的观测到**（1 = 观测到；0 = 被限流吞掉，不等于"没内容"） |

`observed` 这一列是整个数据模型里最重要的一列。它把"观测到 0"和"没有观测"分开了——
没有它，趋势图上那个洞会被读成"这个梗当天没人做"。

## 六、清洗规则清单（按执行顺序）

1. **剥离 HTML 标签**——搜索结果把命中词包成 `<em class="keyword">`，不剥的话
   标题里会混进标签、相关性匹配也会出错。
2. **日期区间校验**——B 站偶尔会把区间外的视频塞进来，`publish_time` 必须落在查询日内。
3. **缺 bvid 剔除**——没有唯一键的记录无法去重，直接丢。
4. **同 bvid 去重**——同一次采集里同一视频可能出现两次。
5. **相关性打分 + 阈值过滤**（≥ 0.5）——见 [03](03_热度量化方案.md) 1.3。
6. **字段规范化**——时间戳转日期、时长字符串转秒、数值字段转 int。

主项目在这一层还多做两件事，Demo 里没有（因为需要跨日数据）：
**同日取更优观测**（同一天两次采集，保留样本数与播放量更好的那次，绝不相加）、
**空窗不清历史**（一次采空只清非本源数据，同源旧快照保留）。

## 七、这个 Demo 的局限（如实说）

1. **样本只有 2 个梗 × 4 天**。它演示的是链路，不是结论。跨梗比较要看主项目的 76 个梗。
2. **只有头部 30 条**。真实采集按 `order=click` 取头部，长尾不在样本里。
   这是刻意的：长尾噪声比例更高，取样越宽越糊。
3. **播放量是"此刻累计"**。老日子的视频多攒了十几天播放，序列天生向今天下坡。
   年龄中性的替代量是 `search_total`。
4. **没有翻页**。`numResults` 显示区间内有 220~1000 条结果，Demo 只取第 1 页。
   主项目同样只取头部，理由是头部是平台可见性的主要来源。
5. **没有 Cookie**。所以拿不到 UP 主空间接口（发现层）和字幕轨（内容层）。
   这两块要登录态，主项目里是可选增强项。
