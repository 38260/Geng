# 赶梗潮｜最终开发提示词 V1

你现在是一名资深全栈工程师 + 数据产品经理 + 前端设计师。

请在当前项目基础上，完成一个可运行、可演示、结构清晰的 Web 数据产品：

# 「赶梗潮」

核心问题：

> **今天该玩什么梗？这个梗现在有多火？现在赶还来得及吗？**

产品定位：

> **一个只分析 Bilibili 网络梗热度与生命周期的数据产品。**

注意：

**这不是普通热搜榜，也不是新闻热点分析平台，更不是 AI Chatbot。**

产品应该让用户第一眼感觉：

> 「这是一个年轻人用来看最近 B 站什么梗正在流行的产品。」

而不是：

> 「这是一个 AI 数据分析后台。」

# 一、核心产品原则

整个项目必须遵循：

> **B站数据负责证明，算法负责计算，LongCat 负责解释，设计负责让人想看。**

具体来说：

- Bilibili 数据 → 原始事实
- 数据分析算法 → 热度指数、增长率、生命周期
- LongCat → 将数据解释成人话、生成“赶梗建议”
- 前端 UI → 将结果变成有趣、直观、年轻化的产品

严禁让 LLM：

- 自己编造数据
- 自己计算热度
- 自己判断不存在的数据趋势
- 直接决定生命周期
- 进行未来 7 天数值预测

# 四、项目边界

## 1. 数据范围

**只分析 Bilibili。**

V1 不加入：

- 抖音
- 小红书
- 微博
- TikTok
- Reddit
- X
- YouTube
- 其他平台

## 2. 分析对象

只分析：

> **网络梗 / Meme**

不是：

- 新闻
- 普通热点
- 明星
- 体育赛事
- 社会事件
- 普通 B 站热门视频

例如：

一个明星突然登上热搜：

> 不一定是梗。

一个新闻事件突然爆火：

> 不一定是梗。

只有能够被明确识别为网络梗，并且符合项目定义的内容，才进入正式梗库。

# 五、核心机制：双 UP 梗认证

这是整个项目最重要的数据规则之一。

使用两个 Bilibili 梗解释 UP 主作为“梗来源”。

## 梗百科

https://space.bilibili.com/1544008396

## 梗指南

https://space.bilibili.com/94510621

## 梗进入正式梗库的规则

只有当：

> **梗百科 + 梗指南**

两个 UP 主都曾经独立发布视频介绍同一个梗时：

才允许该梗进入：

> **「赶梗潮」正式梗库**

流程：

```text
梗百科介绍
      ↓
梗指南介绍
      ↓
双 UP 确认
      ↓
进入正式梗库
      ↓
B站相关视频数据分析
```

必须把这个规则真正实现到数据模型和代码中。

不能只写在 README 中。

# 七、B站数据采集策略

## 不要做

不要尝试：

> “爬取整个 B 站所有视频，然后让 AI 找梗。”

这是不可行且没有必要的。

## 正确方式

采用：

> **梗库驱动 + B站全站搜索 + 定向分析**

即：

```text
双 UP 认证梗
      ↓
提取梗名称 / 别名 / 关键词
      ↓
B站搜索相关视频
      ↓
获取指定时间窗口内的数据
      ↓
相关性过滤
      ↓
去重
      ↓
每日聚合
      ↓
热度计算
      ↓
生命周期判断
```

这里的“全站搜索”指：

> **在 Bilibili 搜索范围内定向搜索某个已认证的梗。**

不是：

> 把 B 站全部视频下载下来。

# 八、数据时间窗口

同时保留：

项目重点不是：

> “这个梗历史上有多少播放量。”

而是：

> **“这个梗最近是不是正在变热？”**

# 十、视频相关性过滤

B站搜索结果不一定全部与目标梗相关。

建立基础相关性过滤。

例如：

```text
TitleMatch
DescriptionMatch
KeywordMatch
```

可以使用：

```text
relevance_score =
    0.6 * TitleMatch
  + 0.2 * DescriptionMatch
  + 0.2 * KeywordMatch
```

再设置合理阈值，例如：

```text
score >= 0.5
```

进入统计。

后续可以增加 LLM 对边界样本进行判断，但：

> **不要让 LLM 判断全部视频。**

# 十一、第一版建议数据规模

如果使用真实数据：

建议第一版：

```text
30～50 个已认证梗
```

每个梗：

```text
最近30天
```

的数据。

不需要一开始追求几十万、几百万条视频。

重点是：

> **形成完整的时间序列。**

# 十二、核心指标：梗热度指数

项目必须拥有自己的：

# 「梗热度指数」

范围：

```text
0～100
```

不要直接使用：

- B站热搜指数
- 单纯播放量
- 单纯点赞量
- 其他平台已有指数

必须通过项目自己的算法计算。

# 十三、热度指数设计

热度可以综合：

```text
播放表现
互动表现
内容规模
参与 UP 主数量
近期增长速度
```

例如：

```text
Hotness =
    w1 * ViewScore
  + w2 * InteractionScore
  + w3 * ContentScore
  + w4 * CreatorScore
  + w5 * GrowthScore
```

具体权重可以根据实际数据进行合理调整。

最终：

```text
0～100
```

# 十四、热度不能简单使用历史累计数据

例如：

一个梗去年有 1 亿播放：

不代表：

> 它现在还火。

因此必须重点分析：

```text
最近1天
最近3天
最近7天
最近30天
```

尤其关注：

```text
最近7天
vs
前7天
```

例如：

```text
视频数量 +68%
评论数量 +51%
弹幕数量 +74%
参与UP主 +42%
```

这些才是判断当前趋势的重要依据。

# 十五、生命周期算法

每个梗需要拥有生命周期状态。

建议：

```text
🌱 萌芽期
📈 上升期
🔥 爆发期
🌊 平稳期
📉 退潮期
🪦 过气
```

生命周期必须由：

> **时间序列数据 + 算法**

决定。

而不是由 LLM 决定。

## 示例

如果：

```text
视频数量持续增长
互动持续增长
UP参与数量增长
```

可以判断：

```text
📈 上升期
```

如果：

```text
短时间快速增长
达到近期高峰
```

可以判断：

```text
🔥 爆发期
```

如果：

```text
连续下降
增长率转负
```

可以判断：

```text
📉 退潮期
```

如果：

```text
长期低活跃
```

可以：

```text
🪦 过气
```

具体阈值需要封装成独立配置，不要散落在前端。

# 十六、AI 的真正作用

AI 不是这个项目的核心数据计算器。

AI 的定位：

> **“把数据讲成人话。”**

V1 只需要两个 AI 能力：

1. 趋势解释
2. 赶梗建议

# 十七、AI能力一：趋势解释

输入：

```json
{
  "hotness": 87,
  "videoGrowth7d": 68,
  "commentGrowth7d": 51,
  "danmakuGrowth7d": 74,
  "creatorGrowth7d": 42,
  "lifecycle": "上升期"
}
```

LongCat 输出类似：

> 最近一周，该梗相关内容增长明显，参与创作的 UP 主数量也在增加，目前仍处于快速扩散阶段。

要求：

- 最多 2 句话
- 自然中文
- 不要说“AI认为”
- 不要重复数字
- 不要写成报告
- 不要胡编数据
- 只能解释输入数据

# 十八、AI能力二：赶梗建议

这是产品最重要的 AI 能力。

核心问题：

> **“现在赶这个梗还来得及吗？”**

输入：

```text
当前热度
热度增长
视频增长
UP主增长
评论增长
弹幕增长
生命周期
距离近期峰值
数据稳定性
```

输出状态只能是：

```text
can_catch
caution
too_late
```

对应：

```text
can_catch → 还来得及
caution → 慎赶
too_late → 你来晚了
```

# 十九、赶梗建议必须遵守

AI：

**不是预测未来。**

不要输出：

> “未来7天热度会达到92。”

不要输出：

> “这个梗明天一定爆。”

不要输出：

> “预计下周增长135%。”

应该输出：

> “最近仍在快速扩散，参与创作的人还在增加，现在赶还来得及。”

或者：

> “热度已经接近近期峰值，新增内容增速开始放缓，想赶可以，但窗口已经比较小。”

# 二十、LongCat 配置

LLM 使用：

> **LongCat**

但：

**不要把 API Key 和 Model 写死。**

创建：

```text
.env.example
```

内容：

```env
LLM_PROVIDER=longcat

LLM_BASE_URL=https://api.longcat.chat/openai/v1

LLM_API_KEY=

LLM_MODEL=LongCat-2.5-Preview

LLM_TEMPERATURE=0.3

LLM_MAX_TOKENS=300

LLM_TIMEOUT=30000
```

用户之后只需要填写：

```env
LLM_API_KEY=你的API_KEY
LLM_MODEL=你的模型
```

即可。

# 二十二、LLM Service 抽象

```text

    └── service
```

业务层只调用：

```text

generateCatchUpAdvice(data)
```

而不是直接调用 LongCat。

这样未来切换模型时不需要修改业务逻辑。

# 二十六、AI容错

AI 永远不能成为核心数据功能的单点故障。

如果：

```text

```

页面依然必须正常显示：

- 热度
- 生命周期
- 图表
- B站数据
- 基础判断

AI部分显示：

> 暂时无法生成赶梗建议

并提供：

> 重新判断

遇到 429：

采用有限次数指数退避。

禁止无限重试。
