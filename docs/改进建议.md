## A. 算法层的真实缺陷（建议优先修）

### A1. `caution_min_heat = 85` 是一条永远不会执行的死规则

**证据**

```
backend/app/analytics/catch_up.py:98
    elif heat >= t.caution_min_heat and peak_gap > 0.10:     # 85.0
```

* 全库最高热度：**80.4**
* `hotness_snapshots` 里 `score >= 85` 的记录数：**0**
* 热度分布：`[80,85)` 只有 1 个，`[85,100)` 为 0

**后果**：那条规则专门写的文案（「热度已经接近近期峰值，增速开始放缓…」）**从来没出现在界面上**。
所有 4 个被标成「慎赶」的梗，走的都是文件末尾的兜底分支：

| 梗 | 热度 | 阶段 | growth | peak_gap | 实际理由文本 |
| --- | --- | --- | --- | --- | --- |
| 闹吃vs古振兴 | 57.6 | 上升期 | **+0.70** | 0.172 | 「数据还在观察，暂时没有明显往上走的迹象」 |
| 野生狗奶 | 53.7 | 上升期 | **+0.62** | 0.222 | 同上 |
| 牛来 | 52.9 | 上升期 | **+0.17** | 0.253 | 同上 |
| 这很难评 | 44.0 | 上升期 | **+0.82** | 0.194 | 同上 |

**这是目前最伤的一处**：一句话里同时出现「上升期」和「没有明显往上走的迹象」，
而且它贴在 growth 高达 +82% 的梗上。用户看一眼数字就会开始怀疑整套系统。
被老师或评委翻到，也最难解释。

**根因**：`can_catch` 要求 `peak_gap <= 0.15`，这些梗的 `peak_gap` 是 0.17~0.25，
于是掉进兜底分支。但兜底文案是按「什么都没有」写的，不是按「在涨但已离峰」写的。

**建议**
1. 立刻把 `caution_min_heat` 降到数据支持的量级。用分位数定，不要拍脑袋：
   当前 P90 约 60、P95 约 70。取 **70**（与 `explosive_min_heat` 对齐）规则即可达。
2. 兜底文案改成中性且真实：「在涨，但已经离开近期峰值，窗口在收窄」。
   不要把「没有往上走的迹象」这种断言塞给一条兜底规则。
3. 加一条回归测试：**每个 `CatchUpThresholds` 字段都必须能被当前数据触发至少一次**
   （或显式标注为刻意不可达）。这条测试能一次性防住同一类问题。

### A2. `creator` 分量几乎是 `content` 分量的复制品

**证据**

```
Pearson r(content_score, creator_score) = 0.9997   (n = 35)
|content - creator| < 2 分的梗：12 / 35，其中 7 个分毫不差
```

数据层的原因在采集侧：

```
backend/app/collectors/bilibili_collector.py:228
    creator_count=len(authors)          # authors = 当日样本里的去重作者
```

而 `analytics/series.py:134` 在 7 天窗口里把它**逐日累加**：

| 梗 | 7 天视频数 | 创作者（日累计） | 单日峰值 | 膨胀 |
| --- | --- | --- | --- | --- |
| 闪身步 | 100 | 100 | 20 | **5.0x** |
| 闹吃vs古振兴 | 28 | 28 | 6 | **4.7x** |
| 野生狗奶 | 90 | 88 | 20 | 4.4x |

即：`creator_count / video_count` 约为 1.0（库里有 1,011 行 `creator_count == video_count`），
窗口合计只是「视频数」换了个名字，再乘上跨日重复计人的膨胀系数。

**后果**：热度公式里 `content` 0.16 + `creator` 0.14 = **0.30 实际全给了「内容量」**，
设计意图是 0.16 给内容量、0.14 给「有多少人在参与」。
`log_score` 单调，两个分量排序完全一致，等于把一个因子数了两遍。

**代码自己也知道**：`series.py:48` 写着 `creator_peak` 是「去重后的下界」，
但 grep 显示 **`creator_peak` 只被赋值、从未被读取**。

**建议**（按性价比排序）
1. 最小改动：公式里把 `cur.creator_count` 换成 `cur.creator_peak`。
   单日峰值是去重后的下界，至少不再随天数线性膨胀。
2. 正确改法：聚合层按 `author mid` 跨日去重，得到「本周参与 UP 主数」。
   采集时把 `author mid` 一起入库（现在只存名字，同名或改名会串）。
3. 无论怎么改，补一条测试：`creator_score` 与 `content_score` 的相关系数必须 < 0.95。

### A3. `search_total` 被写入但从未参与计算

**证据**

* `meme_daily_stats` 有 `search_total` 列，2,209 行全部非空，其中 833 行 > 0
* 读取点只有 `models/stats.py`（序列化）与 `models/base.py:126`（判断空洞）
* `analytics/hotness.py` 里**没有任何引用**

而 README 自己写过：`search_total` 是「年龄中性的替代量（实测上周 789/天 vs 这周 750/天）」——
这是全库最干净的一个对照信号，现在只躺在表里。

**建议**：要么用它（例如用 `search_total` 校正 `view` 的年龄偏差，或作为第六个分量并同步做消融），
要么明确删掉它、并删掉文档里那句「替代量」。中间状态最糟：写了不用，等于给了错误的心理预期。

### A4. 观测闸门是硬开关，8 个梗卡在边界正下方

```
观测 0 天: 5     1 天: 5     2 天: 4     3 天: 4   <- 闸门线以下，共 18 个
观测 4 天: 3     5 天: 4     6 天: 5     7 天: 5
```

`min_observed_days = 4` 是一条硬线：观测 3 天则置信度 **0**、阶段「数据不足」；
观测 4 天则正常出结论。**8 个梗卡在 2~3 天**，多补一天观测就能翻转结论。

**建议**：把「给不给结论」改成置信度加权——观测 7 天置信度满，5 天打 0.8，
4 天打 0.6，3 天打 0.4 且**只否决 `too_late` / `obsolete` 这类强断言**。
这样既保住「不给没有地基的结论」这个立场，又不会因为一天之差把梗判成「不知道」。

### A5. 两个从未被使用的配置项

| 配置 | 位置 | 状态 |
| --- | --- | --- |
| `plateau_band = 0.12` | `config/algorithms.py:164` | 全仓库**无引用**；平稳期实际是 `classify()` 的兜底 else，没有任何显式规则 |
| `creator_peak` | `analytics/series.py:48,135` | 只赋值不读取（见 A2） |

**建议**：要么删掉，要么补上实现。留着一个「看起来在调参、其实没接线」的旋钮，
比没有这个旋钮更危险——下次有人改 `plateau_band` 会以为生效了。

### A6. 阈值全是经验值，还没有实证依据

26 个阈值参数，注释写得很清楚，但**没有一个是搜索或拟合出来的**：

```
explosive_min_heat = 70.0     explosive_min_growth = 1.30
rising_min_heat = 30.0        receding_min_peak_gap = 0.20
obsolete_max_heat = 18.0      sprouting_max_view_7d = 80_000     ...
```

这个项目**已经做过一次证伪实验**（解说播放量 vs 热度，r = +0.40，R² 约 0.16），
说明你已经有这套方法论。同样的手法用在阈值上，成本很低。

**建议**：拿现有 71 个梗跑一次网格搜索，看阶段分布对阈值有多敏感；
输出一张「阈值 ±20% 时阶段翻转的梗数」热力图。哪怕不做人工标注，
这张图也能回答「你的阶段划分稳不稳」——而这是评委一定会问的。

## B. 数据层的具体问题

### B1. 只有 8 个梗是「双 UP 已核验」

```
bilibili + verified_both :  8
bilibili + partially     : 27
bilibili + unverified    : 27
```

根因是风控：匿名只能取到每位 UP 主最近约 150~400 条投稿，深翻页被 -352 / 412 挡住。
这一个瓶颈同时压着三件事：认证强度、字幕数量（`video_transcripts` = **0 条**）、
以及梗介绍只能退回「标题 + 简介拼」。

**建议**：配 `BILI_COOKIE` 跑一轮 `rebuild_from_bilibili --pages 20 --refresh-index`，
把 27 条 `unverified` 里的真实梗升级为已核验。这是**投入产出比最高的一次性动作**——
一个 Cookie 同时解开认证、字幕、介绍三个卡点。

### B2. 11 条梗的 `data_source` 是空串，名字明显是抽取噪声

```
id=62  突然出现的章鱼哥的美妙音乐啥
id=65  x姆？长月老贼
id=91  我简直就是佐助本人
...（共 11 条，全部 status=certified 且通过准入，但数据来源为空）
```

它们既不是 `bilibili` 也不是 `mock`，所以既进不了真实榜单、也不带演示标注。
名字里带 `x姆？` 这种占位形态，说明发现层在做「标题到梗名」抽取时没清洗干净。

**建议**：在 `list_recent_certified` 的抽取阶段补一条与「XX在哪？最优骑士小碎步」
同类的占位名拒收规则（README 说已有，实测漏了 11 条）；
并把 `data_source` 设成 `NOT NULL` + 默认值，避免出现第三种「无来源」状态。

### B3. 一对「互为子串」的梗，跨了真实与演示两条线

```
id=18  松弛感家长    aliases=["松弛感"]     data_source=mock
id=22  松弛感        aliases=["很松弛"]     data_source=bilibili
```

「松弛感」是「松弛感家长」的别名。因为 `data_source` 不同，一个走真实采集、
一个走演示数据，两边的相关性过滤会互相污染。
另外「松弛感」是口语常用词，正是 README 里说过的「梗名是常用口语时会被模糊匹配」的典型。

**建议**：跨 `data_source` 做一次别名占用检查——真实梗的别名不能被演示梗占着。
顺手把「松弛感」按弱别名规则处理（它同时也是梗名，需要更严的佐证）。

## C. 工程与验证层

### C1. 前端 4,666 行 TS/TSX，测试为 0

```
backend/tests    : 20 个测试文件（252 项）
miniprogram/tests: 4 个测试文件（21 项）
frontend/src     : 0 个测试文件  <- 且 package.json 里没有任何测试依赖或 test 脚本
```

前端确实有**值得测的纯逻辑**，不是纯展示：

* `types/api.ts` 494 行类型声明——接口契约全靠类型，没有运行时校验
* `utils/format.ts` 的 `compact()` / `percent()` / `growthClass()`，含一条反直觉业务规则
  （「增幅颜色跟随阶段，而不是涨绿跌红」），没有任何测试守着
* `MemeDetail.tsx` 569 行、`Manage.tsx` 575 行的数据组装逻辑

**建议**：加 `vitest` + `npm test`，先只覆盖 `utils/format.ts` 和「trend 接口返回后怎么拼图」。
成本约半天，收益是前端不再完全黑箱。另外 `types/api.ts` 建议用 zod 之类做一次运行时校验——
后端字段一改，前端现在是**静默出错**而不是报错。

### C2. 观测覆盖度只有 55.3%，且 10 个梗是 0 覆盖

```
coverage 0.0 : 10 个        coverage 0.9 : 11 个
coverage 0.1 :  8 个        coverage 1.0 : 17 个
coverage 0.3 :  8 个        中位数 0.571   均值 0.554
```

现在的应对是「重试 + 同日取优」，把单日覆盖从 40% 提到 87%，这是对的。
但仍有近一半的梗在 7 天窗口里看不全。

**建议**：换思路——**降低对逐日完整性的依赖**，而不是继续跟风控硬碰：
* 用 `search_total` 做一个周粒度的稳健指标（周合计本来就比日序列抗洞）
* 对覆盖 < 4 天的梗，用「相邻周对比」代替「7 天 vs 7 天」，把窗口拉长换观测数

### C3. 样本量小这件事没有真正的解法（诚实记账）

n = 31 的证伪实验、71 个入池梗、2,209 行日统计。深度模型撑不起来，
阈值也没有足够数据去拟合。短期无解，只能靠时间累积并把结论说得更保守。
**建议**：论文里写成「方法贡献不依赖大样本，但一致性检验的统计功效有限」，
主动限定结论边界，比被追问时找补好。

## D. 最大的战略缺口：没有 ground truth

上面所有问题的**共同上游**是同一件事：**没有人标注过「这个梗当时到底算不算火」「这个阶段判得对不对」。**
因为它不存在，所以：

* 阈值无法被学习，只能靠经验（A6）
* 准确率无法被计算，只能报一致性实验的**计划**（结题 deck 第 9 页那四块空白）
* `caution_min_heat = 85` 这种错误不会被任何指标暴露（A1）
* `creator` 与 `content` 重复计数不会被任何指标暴露（A2）

**这是我认为最该先做的一件事**，而且它不贵：

1. 抽 **30 个梗 x 7 个时间点 = 210 条**，用现在的界面做成两选一或六选一的标注题。
2. 找 **3 个人独立标**，先算 Fleiss' Kappa 看**标注者之间**一致不一致。
   如果人自己都只有 Kappa 0.4，那「规则准确率」这个指标本身就没有意义——
   这个结论**比任何准确率数字都值钱**，而且能直接写进论文。
3. 人一致了，再和规则判的结果比，出混淆矩阵。

有了这 210 条，A6 的阈值搜索、一致性检验、论文里那套评估报告才能从「计划」变成「结果」。

## E. 被我验证为「不成立 / 影响很小」的假设（也记下来）

诚实起见，这些我怀疑过、但实测站不住，**不建议花时间**：

| 假设 | 实测结果 |
| --- | --- |
| 滚动热度序列尺度不一致（早期窗口天数少）会显著扭曲 `peak_gap`，导致 `explosive` / `receding` 判错 | 改用「只用完整 7 天窗口」重算，`peak_gap` 变化不小于 0.10 的梗数：**0 / 35**。方向存在，影响可忽略 |

## G. 已实施（2026-09-29）

### G1. A1 —— 死阈值与自相矛盾的文案（P0）

改动：
* `CatchUpThresholds.caution_min_heat` **删除**。它先被从 85 降到 70，
  但热度 ≥70 的梗全库只有 1 个、且其 `peak_gap` 是 0.018，仍然是"技术上可达、
  实际上不干活"——那是**在重复同一个错误**：拿真实数据的分位数挑一个好看的数，
  而规则本身没有信息量。
* 判据换成 **`peak_gap`**：`caution_min_peak_gap = 0.10`、
  `caution_strong_peak_gap = 0.20`。"离开峰值多少"才是"窗口还剩多大"的直接度量，
  热度高低交给上升/爆发/退潮那几条规则去管。
* 规则**位置**移到 `can_catch` 之后。放在前面会把 `peak_gap` 落在
  `[0.10, 0.15]` 的梗全部吃掉，明明在快速扩散却永远拿不到"来得及"。
* 兜底文案改为不替数据下结论：「热度和增速都还没有明确方向，现在赶性价比一般…」。
* `CatchUpResult` 新增 `rule` 字段，记录**具体命中了哪条规则**。
  同一种 `status` 可能由多条规则产出（"慎赶"就有 5 个来源），
  只看 status 无法测试也无法排查。

效果（真实数据）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 「慎赶」 | 4 个，理由全是「没有明显往上走的迹象」 | 8 个，理由为「已离开近期峰值一段，窗口明显收窄」（7 个）/「一点」（1 个） |
| 「还来得及」 | 19 个 | 15 个 |
| 高热度慎赶规则 | 从未命中 | `off_peak_mild` ×1、`off_peak_strong` ×7 |
| 上升期的理由与自身 growth | 出现「上升期 + 没有往上走的迹象」（growth +82%） | 8 个上升期梗逐条核对，0 处矛盾 |

### G5. P0-2 —— 守住这一类的回归测试（P0）

新增 `backend/tests/test_threshold_reachability.py`（27 项）。它做三件事：

1. **每个阈值两侧构造边界用例**，确认阈值真的在参与判定。
2. **断言关键阈值落在真实数据可达的范围内**（就是这次 bug 的守门人）。
3. **断言兜底文案不得与输入矛盾**：扫一遍高增长区间，
   任何一条理由都不许把在涨的梗描述成"没有往上走的迹象"。

**一个设计教训值得记下来**：这组测试的第一版用「扰动阈值 → 看输出是否改变」
来判断可达性，结果对兜底规则**全部误报**——把 `receding_max_growth` 抬高到 -0.2 后，

阈值本身参与边界计算，输入不可能与阈值脱钩。

另外顺手修了既有的 `test_catch_up.py::test_at_peak_but_decelerating_is_caution`：
