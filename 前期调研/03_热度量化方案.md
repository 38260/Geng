# 03 · 如何量化

> 对应分工第 3 项：设计一个能正确表达"热度"的指标，以及用什么算法准确得到它。
> 所有阈值都集中在 `backend/app/config/algorithms.py`，本文与代码逐条对应。

这一节分四步：**先定义梗是什么**（不然没法度量），**再定热度公式**，
**然后定生命周期与赶梗判断**，**最后说怎么证明这套东西是对的**。

---

## 一、先把对象定义清楚

### 1.1 什么是"梗"（本项目口径）

> **B 站两位解说 UP 主「梗百科」（mid=1544008396，日更）或「梗指南」（mid=94510621，周更）
> 的视频里介绍过的东西，就是我们项目里的"梗"。**

这是一个**操作性定义**——它不追求把"梗"这个文化概念定义完整，只追求**可执行、可复现**。
选择这两个账号做"存在性证明"的理由：他们是专门做"这是啥梗"的账号，
一期视频对应一个梗，标题里通常直接写着梗名，抽取规则稳定。

**为什么是并集而不是交集？** 这是被真实数据打脸后改的。最初口径是"两位都介绍过"（交集），
实测 90 天内梗百科介绍过 37 个、梗指南 22 个，**交集只剩 8 个**——
日更账号的选题被周更账号的排期一票否决，当时热度第一的「闪身步」就在库外。
现在改成**并集准入**，同时把"双 UP 认证"降级成可信度标签（`cert_label`）：

```
准入（进梗库）  = 梗百科介绍过  OR  梗指南介绍过      → 并集
认证（挂徽章）  = 梗百科介绍过  AND 梗指南介绍过      → 交集
```

**认证窗口 90 天滚动**（`CERT_WINDOW_DAYS`），比报告窗口（30 天）长——
因为解说视频通常比梗的爆发期早 1~2 周，两个窗口合成一个会漏掉正在热的梗。

### 1.2 一个梗对应哪些视频

对每个梗、每一天，用**日期区间查询**取当天播放量最高的 20~30 条相关视频作为样本：

```
keyword = 梗名（常用口语词时退回别名）
order   = click（播放量降序）
pubtime_begin_s / pubtime_end_s = 那一天 00:00 ~ 次日 00:00
```

所以本项目的「当日播放量」= **该日头部相关视频的合计播放量**，不是该梗全站绝对量。
跨日、跨梗用的是同一把尺子，形状与排序可信；绝对值不可外推。这一点明写在产品里。

**为什么必须带日期区间？** 不带的话，B 站返回的主要是最近发布的内容，
历史那几天的播放量是拿今天的数据回填的——第一版这么做，算出了 **+23,616%** 的假增长。

### 1.3 "相关"怎么判：0.6 / 0.2 / 0.2

搜索结果不会全部真的与目标梗相关，进统计前先打分：

```
relevance = 0.6 × 标题分 + 0.2 × 简介分 + 0.2 × 关键词覆盖率
进入统计的条件：relevance ≥ 0.5
```

其中标题分与简介分是**互斥取最高档**，不是相加：

| | 梗名命中 | 长别名（≥4字） | 短别名（2~3字） | 关键词命中 |
| --- | --- | --- | --- | --- |
| 标题分 | 1.0 | 0.85 | 0.5 | 0.5 |
| 简介分 | 1.0 | 0.6 | 0.6 | 0.4 |

**短别名只算弱证据**（`STRONG_ALIAS_LEN = 4`）——这是踩过的坑：
「我不是黄豆」的别名写成"黄豆"，418 条样本里 **343 条**其实在讲炒黄豆、黄豆版琵琶曲，
而它当时还挂着榜首。中文 2~3 字别名基本就是常用词，单独命中不足以判定相关。

**这个阈值有多严？** 只在简介里提到梗名的视频拿到 0.2 分，会被过滤掉。
也就是说：进统计的样本，标题里真的出现了这个梗。
在我们 2026-10-05 抓的 120 条真实原始记录里，**35 条（29.2%）被这条规则挡掉**——
挡掉的基本都是"标签里蹭了一个梗名、标题里根本没有"的视频。见 [04](04_数据源与处理Demo/)。

## 二、热度指数（RQ1：这个梗现在有多火）

### 2.1 公式

```
热度 Hotness = 0.25 × 播放分 + 0.20 × 互动分 + 0.16 × 内容规模分
             + 0.14 × 参与UP主分 + 0.25 × 增长分
```

权重与阈值（`HotnessWeights`）：

| 分量 | 权重 | 度量 | 参考区间（7 天窗口） |
| --- | --- | --- | --- |
| 播放 view | 0.25 | 7 天头部样本播放合计 | 3,000 ~ 8,000,000 |
| 互动 interaction | 0.20 | 7 天评论 + 弹幕 | 300 ~ 900,000 |
| 内容规模 content | 0.16 | 7 天相关视频数 | 1 ~ 900 |
| 参与 UP 主 creator | 0.14 | 窗口内单日去重作者峰值 | 1 ~ 500 |
| 增长 growth | 0.25 | 最近 7 天 vs 前 7 天 | 见 2.3 |

### 2.2 关键设计一：对数区间归一化

绝对量先做**对数区间归一化**再进加权：

```
score = 100 × (ln(x) - ln(floor)) / (ln(ceiling) - ln(floor))，再截断到 [0, 100]
```

**为什么不用线性归一？** 因为播放量差三个量级。一个亿级老梗和一个十万级新梗，
线性归一之后新梗永远是 0 分。取对数之后，量级的差异被压缩成可比的距离，
"一条爆款视频吃掉整个榜"这件事就不会发生。

`floor` 与 `ceiling` 是刻意设的：低于 floor 的噪声不给分，高于 ceiling 的不再增益。

### 2.3 关键设计二：增长权重给到 0.25

这是整个指数里最重要的一个决定。产品要回答的是"**最近是不是正在变热**"，
所以一个历史累计 1 亿播放、但这周没人做的梗，不该排在前面。

增长分只看**最近 7 天 vs 前 7 天**，然后线性映射到 0~100：

```
增长率 -30%  → 0 分
增长率 +120% → 100 分
```

（`GROWTH_SCORE_ZERO = -0.30`，`GROWTH_SCORE_FULL = 1.20`）

**三条防噪声的约束：**

1. **样本不足不外推**：7 天窗口内相关视频 < 3 条（`MIN_SAMPLE_VIDEOS`）时，
   增长率置空，整体分数打 0.6 折（`LOW_SAMPLE_DAMPING`）。
   考古区冒出一条视频不算 +100%。
2. **增幅要有基数**：前 7 天讨论量 < 30（`MIN_GROWTH_DISCUSSION`）时不报百分比，
   界面显示"—"。基数 3 涨到 20 也是 +567%，但那是噪声。
3. **不把"没观测到"当成"没内容"**：见第四节。

### 2.4 关键设计三：一个踩过的坑（答辩加分项）

`creator` 这个分量原本是 `content` 的复制品。采集层给的 `creator_count` 是
**当日去重作者数**，而样本里几乎每条视频来自不同作者——
`creator_count / video_count` 的中位数是 **1.000**，库里有 **1,011 行**两者相等。
聚合层再逐日累加，它就成了"视频数换个名字"。

实测 `content` 与 `creator` 两个分量的相关系数一度是 **r = 0.9997**——
`0.16 + 0.14 = 0.30` 的权重，实际上全压在了一个因子上。

改用 `creator_peak`（窗口内单日去重峰值，这个值本来就算好了、却一直没被读取）之后，
r 降到 **0.952**，扣掉 `content` 能解释的部分，还剩约 **31%** 的独立变异。
榜首从 81.0 变成 **76.8**——那 4 分，是我们自己的重复计权。

> 仍未解决：真正的去重需要按 author mid 跨日求并集，而库里只存了作者名、没存 mid。

## 三、生命周期与赶梗判断

### 3.1 六个阶段

🌱 萌芽 → 📈 上升 → 🔥 爆发 → 🌊 平稳 → 📉 退潮 → 🪦 过气

规则**自上而下匹配，第一条命中即判定**。判定只用四个可观测量：

- `heat` 当前热度指数（0–100）
- `growth` 最近 7 天 vs 前 7 天的综合增长率
- `peak_gap` 距 30 天内热度峰值的回落幅度（0 = 正在峰值上）
- `activity` 最近 7 天新增相关视频数
- `view_7d` 最近 7 天播放量
- `stale_days` 距今多少天没有新内容

主要阈值（`LifecycleThresholds`）：

| 阶段 | 判据 |
| --- | --- |
| 🪦 过气 | 连续 14 天无新内容，或（活跃 ≤ 2 且热度 ≤ 18） |
| 🌱 萌芽 | 活跃 ≤ 10 且 7 天播放 ≤ 8 万 且 热度 ≤ 45 |
| 🔥 爆发 | 热度 ≥ 70 且 增长 ≥ +130% 且 距峰值 ≤ 0.15 |
| 📈 上升 | 增长 ≥ +15% 且 热度 ≥ 30 |
| 📉 退潮 | 增长 ≤ -12%，或 距峰值 ≥ 0.20 且连续下滑 ≥ 3 天 |
| 🌊 平稳 | 以上都不命中（\|增长\| 很小），显式规则 |

> 爆发期的增长门槛（+130%）刻意高于上升期（+15%），否则"涨得快的上升期"会被误判成爆发。

### 3.2 第七个状态：数据不足（不是阶段）

```
最近 7 天真正观测到的天数 < 4  →  拒绝给阶段、拒绝给赶梗结论，置信度记 0
```

（`min_observed_days = 4`）

**为什么必须有这个闸门？** 因为 B 站匿名搜索会随机把有内容的日子返回成空壳
（实测单次命中率约 40%）。洞太多的时候，增长率和退潮判的都是**接口抖动**，不是梗本身。

这一条只影响**趋势结论**，不影响热度排序与上榜门槛——那用的是存量水平，跨梗同一把尺子。
界面上不把"数据不足"画进时间轴，因为它不是第七个阶段。

### 3.3 赶梗判断（RQ3：现在赶还来不来得及）

由热度与阶段输出三态（`CatchUpThresholds`）：

| 状态 | 判据 |
| --- | --- |
| 🔴 你来晚了 too_late | 增长 ≤ -10%，或 距峰值 ≥ 0.25，或阶段 ∈ {退潮, 过气} |
| 🟢 还来得及 can_catch | 增长 ≥ +10% 且 距峰值 ≤ 0.15 且 阶段 ∈ {萌芽, 上升, 爆发} |
| 🟡 慎赶 caution | 距峰值 ∈ [0.10, 0.35]（窗口在收窄） |
| ⚪ 说不准 | 观测不足，闸门拦截 |

**这里也有一条死规则的教训。** "慎赶"原本写的是 `heat >= 85`，而全库最高热度只有 80.4，
`score >= 85` 的记录数是 **0**——规则一次都没执行过，所有"慎赶"都是文件末尾的兜底分支产出的，
而兜底文案写的是"没有明显往上走的迹象"，它最后贴在了一个增长 +82% 的上升期梗上。自相矛盾。

把 85 改成 70 也救不了：全库热度 ≥ 70 的梗只有 1 个。
于是判据整个换掉：不看"热度多高"，看**"离开峰值多远"**（`peak_gap`）——
那才是"窗口还剩多大"的直接度量。现在 `peak_gap` 落在 0.10~0.35 的梗有 9 个，规则真在干活。

### 3.4 上榜门槛：准入 ≠ 上榜

```
热榜 = 通过发现层准入（并集）
      ∧ 认证窗口内还有真实解说证据
      ∧ 有指标快照
      ∧ 阶段不是"过气"
      ∧ 近 7 天头部播放 ≥ 1 万
```

**刻意不用"有内容天数"当门槛**：「琵琶曲」30 天只有 4 天有内容，但那几天播了 3,976 万，
按天数卡会误杀脉冲型梗。`active_days` 只作为诊断量存进快照。

实测效果（2026-09-28）：31 个入池有数据的梗 → 12 个上热榜，
被挡掉的 17 个全是过气、2 个只剩残值。

## 四、"没看见"不等于"没有"：数据质量方法

这是本项目最有含金量的部分，也是答辩最值得讲的一段。

### 4.1 两种"空"

B 站匿名搜索返回两种完全不同的"空"：

| 返回体 | 含义 | 能不能记成 0 |
| --- | --- | --- |
| `{"result": [], "numResults": 0}` | **可信**：当天确实没有内容 | 可以 |
| `{"v_voucher": "voucher_xxx"}` | **不可信**：HTTP 200、无错误码，结果被吞 | **不行** |

旧实现把两者混成 `rows == []`，于是库里 2,036 行日统计里 **1,412 行**是这种假零——
超过三分之二。用户实测打脸：你们说琵琶曲在退潮，可它每天还有 700~1,000 条新视频。

**现在的处理**：检出 `v_voucher` 就抛 `BilibiliThrottled`，不返回空列表；
每天最多重试 `collect_day_retries + 1` 次；仍拿不到就写 `observed=0`；
命中限流触发会话冷却。

### 4.2 四类数据质量问题的处理

| 问题 | 现象（实测） | 处理 |
| --- | --- | --- |
| 假增长 | 一次抓完再摊到每天，算出 **+23,616%** | 逐日带时间区间查询 |
| 抽样抖动刷薄 | 琵琶曲从 4 天 / 3,976 万被刷成 1 天 / 18 条，热度 44.2 → 0.0 | **同一天只保留更好的一次观测**（比样本数与播放量），绝不相加 |
| 空窗误删 | 一次采空就把历史真实数据清掉 | 空窗只清非本源数据，同源旧快照保留并计数 |
| 口语化梗名模糊匹配 | "黄豆"别名导致 418 条样本里 343 条污染 | 短别名只算弱证据，需第二个词佐证 |

### 4.3 已知未修的口径偏差（如实写出来）

`view` 是"该日发布的 cohort 在被查那一刻的累计播放"，老日子多攒了十几天，
序列天生向"今天"下坡，所以 7 天 vs 前 7 天的增长率**偏高估跌**。

年龄中性的替代量是 B 站返回的当日结果总数（`search_total`，实测上周 789/天 vs 这周 750/天）。
改这个要重排热榜与全部赶梗结论，2026-09-28 决定先修可信度、暂不动公式。
**这一条在答辩时被问到"你的指标有什么已知缺陷"时，可以正面回答。**

## 五、怎么证明这套东西是对的（验证方案）

一个自造的指数，最容易被问的就是"你怎么知道它准"。我们的回答分四层。

### 5.1 阈值可达性检验（已做，有测试守着）

**这是最有说服力的一条**，因为它抓到的是真 bug。

`backend/tests/test_threshold_reachability.py` 对**每一条阈值**构造边界用例，
确认阈值两侧给出不同结论，并断言关键阈值落在真实数据可达的范围内。

为什么需要它：`heat >= 85` 这条死规则之所以长期没被发现，是因为原来的测试用例传了
`heat = 96.0`——**一个现实中不存在的分数**。它不是逻辑写错了，是**可达性**没有被检验。

> 一句话：**模型不会告诉你，它的输入永远不会出现。**

### 5.2 人工标注一致性（计划中）

对 30 个梗由 3 名标注者独立判断所处阶段，计算：
- 标注者之间的一致性（Cohen's Kappa / Fleiss' Kappa）
- 规则判定 vs 人工判断的混淆矩阵
- 热度排序 vs 人工排序的 Spearman 相关

### 5.3 权重消融（计划中）

每个分量权重 ±0.05 重跑，看榜单排名的 Spearman 相关掉多少。
如果权重微调就导致排名大乱，说明指数不稳。

### 5.4 基线对比（计划中）

用 ARIMA 或简单线性外推做热度预测，与规则判定做混淆矩阵比较。
目的不是证明规则引擎更好，而是**给出一个参照系**。

### 5.5 已经做完的一次证伪实验

把"解说视频播放量高就说明这个梗值得做"这个直觉，放到 31 个上榜梗上检验：

- Pearson **r = +0.40（p = 0.028）**
- Spearman **rho = +0.29（p = 0.12，不显著）**
- R² ≈ 0.16

反例同时存在：「闪身步」解说只有 64.6 万播放，梗本身热度榜首；
「宗主第二招」解说是 160.7 万，梗本身热度 **0.0**。

结论：解说播放量衡量的是那个账号自己的粉丝盘，适合做**采集成本的预算筛**，
不能当准入判据。于是产品规则被改了——这就是"先立一个可被数据推翻的判据，再拿真实样本去检验它"。

## 六、算法边界（明确不做什么）

1. **不做未来数值预测**。不说"下周多少分"。
2. **LLM 不参与任何数值或状态判定**。它只把算法结论翻译成人话；模型返回的 `status`
   与算法不一致时以算法为准；文案里出现"预计/未来 7 天/一定会爆"这类预测口吻直接丢弃。
3. **不做多平台**。先把 B 站这一把尺子做准。
4. **该停手时停手**。采集遇到硬风控（HTTP 412 / `code=-352`）连续 3 个梗就中止整批。
